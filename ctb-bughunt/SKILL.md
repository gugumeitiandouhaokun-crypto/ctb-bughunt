# ctb-bughunt：找 bug 测试用例开发

目标：针对题目给出的被测系统，写出在**无 bug 版本上全部通过**、在植入 bug 的版本上**检出尽量多 bug** 的测试用例。
方法论：**快速探测打基线 → 提交拿到命中 → 每轮一个主题深入探测、录制新场景、相对已探索范围有新增才提交 → 复盘后自动进入下一轮**。场景用生成脚本描述超大密集多对象步骤，由无 bug 版本录制得到逐条精确断言。
参考资料按需读取：每一步的"读"列出进入该步时才需要的文档章节，不要一次读完全部参考资料（读取方式见文末"参考资料"）。

本 skill 不针对任何具体题目：命令、返回码、业务类都从题目描述、反编译源码和真实返回中获得；脚本给出的自动识别结果都是草稿，由你审阅确认。

## 脚本位置与调用方式

`<SKILL>` 指本 SKILL.md 所在目录，常见位置（存在哪个用哪个）：
- `~/.config/opencode/skills/ctb-bughunt`（Windows：`%USERPROFILE%\.config\opencode\skills\ctb-bughunt`）
- 项目内 `.opencode/skills/ctb-bughunt`

所有操作都通过统一入口完成，**在题目工作目录（cwd）下执行**：

```
python "<SKILL>/scripts/ctb.py" <子命令> [参数]
```

| 子命令 | 作用 |
|---|---|
| `cookies` | 获取/刷新 iLearning 登录 Cookie（弹出浏览器免密登录） |
| `pull --subject <题目ID或URL>` | 拉取题目描述、框架、jar 与服务端代码到 `answer/`，保存原件到 `notes/pristine/`，`udpPort` 改为本工作目录专用端口 |
| `decompile` | 反编译 `answer/` 下的无 bug jar 到 `decompiled/src/`，生成 `decompiled/index.md` |
| `analysis [--done]` | 查看 `notes/题目分析.md` 是否已固化、哪些章节为空；`--done` 记录分析对应的题目描述与 jar 指纹（之后题目或 jar 变化会提示复核） |
| `spec [--force]` | 从题目描述与反编译源码起草接口规格 `notes/spec.json`（命令、返回码形态、各命令返回码），需审阅 |
| `probe -f <命令文件>` / `probe -c "<命令>"` | 探针：启动无 bug 程序逐条发送命令，打印真实返回与耗时，记录到 `notes/probes/` |
| `record --gen <生成脚本>` / `record -f <步骤文件>` | 录制：在无 bug 程序上双跑步骤，生成数据表断言写入 `testaw.py` / `udpunittest.py`，随后打印矩阵缺口并自动 `check` + `local`；`--dry-run` 只出报告不写文件，`--coverage` 同时统计分层覆盖率与每个测试的贡献，`--name` 指定录制名称 |
| `matrix` | 接口 × 返回码矩阵：汇总录制与探针的真实返回，与 spec 对照列出未调用、未触发、单一返回码、规格外 |
| `coverage` | 带 JaCoCo 跑一次 `local`（含手写用例），输出分层覆盖率到 `notes/coverage/` |
| `check` | 提交前规范检查（框架铁律、Python 3.8 语法、标准库、残留文件等） |
| `local` | 在无 bug 程序上运行 `answer/udpunittest.py`，以日志 `Ran N tests ... OK` 判定 |
| `run` | 平台调试（type=2）：先 `check` + 带覆盖率的 `local` 全部通过再上传；打印本版本相对已探索范围的新增；结果只说明代码能否在平台正常运行（判题状态、报错、代码质量扣分），**不含 bug 命中**；判题结果进 `notes/judge/` |
| `submit --yes [--reason "<维度>"] [--no-prune]` | 正式提交（type=1，成绩以最后一次提交为准）：要求当前答题文件已 `run` 过，且相对已探索范围有新增覆盖行、分支或返回码（没有时需 `--reason` 写明本轮新的场景维度）；输出 bug 检出表，记录命中、追加场景库并精简用例（`--no-prune` 只记录不删除）；提交时的答题文件存到 `notes/submits/`，覆盖行与返回码并入已探索范围 |
| `restore [--name <记录名>]` | 把答题文件恢复为某次正式提交时的版本，默认检出最多的一次 |
| `hits` / `prune` | 查看命中记录与场景库摘要 / 对最近一轮提交执行精简（`--no-prune` 之后使用） |
| `stop` | 停止本工作目录的被测程序（按端口查进程） |
| `wait [--sec N]` | 等待后台任务最多 N 秒（默认 50），打印新增输出；任务结束时打印"后台任务结束"与退出码 |
| `cancel` | 终止后台任务并停止被测程序 |
| `status` / `info` | 查看本地进度、轮次、已探索范围与后台任务 / 平台题目状态与提交记录 |

`run`、`submit`、`local`、`coverage`、`record` 默认在后台执行：命令启动任务后最多等待 50 秒，期间结束则直接输出完整结果；未结束时输出"后台任务进行中"并返回，之后用 `ctb.py wait` 继续等待，直到出现"后台任务结束"。同一工作目录同时只允许一个后台任务。加 `--fg` 在前台执行（仅用于命令行工具没有超时限制的环境）。

依赖：Python 3.10+（`pip install requests selenium`）、`java` 在 PATH 中（JRE 即可）、iLearning 免密登录环境。

## 工作目录

每道题使用一个独立的空目录（覆盖率要求路径为纯英文、无空格，或系统可生成短路径）：

```
<work>/
  cookies.json
  answer/       题目与框架；提交的就是这里的 testaw.py、udpunittest.py
  decompiled/   src/ 反编译源码，index.md 类/方法/字符串常量索引
  notes/        ctb.json、pristine/、probes/、judge/history.md、local_last.txt/.json
                题目分析.md  对题目与接口的理解（固化后代替重读题目描述与源码）
                数值模型.md  探针确认的返回格式、约束、公式与常量
                复盘.md      每轮主题、新增范围、检出变化与下一轮候选主题
                场景库.md    每次正式提交后每个用例的场景、规模与命中情况（自动追加）
                hits.json    命中轮次记录与场景步骤指纹
                explored.json 已探索范围：历次正式提交的用例执行过的业务代码行与触发过的返回码
                submits/     每次正式提交时的答题文件与检出结果
                spec.json  接口规格（spec.auto.json 为上次自动提取结果，勿手改）
                matrix.md  接口 × 返回码矩阵
                steps/     生成脚本与其输出的步骤
                record/    录制报告 <名称>.md 与原始结果 <名称>.json
                coverage/  覆盖率报告、history.md、scope.json（可选，人工指定分层）
```

## 流程

分两段：**基线轮**达到质量门槛就第一次正式提交，不追求矩阵与覆盖率做满；之后进入**迭代轮**，每轮一个主题，提交并写完复盘后直接开始下一轮，不停下等待用户，直到满足停止条件。

### 第 0 步：会话开始（每次新会话或上下文被压缩后）

- `ctb.py status`。显示后台任务运行中时，先 `ctb.py wait` 直到结束，再继续。
- 题目分析显示"已固化"：读 `notes/题目分析.md`、`notes/数值模型.md`、`notes/复盘.md`、`notes/场景库.md`（存在的话），不重读题目描述与源码。
  - 轮次为基线轮：从基线轮中尚未完成的步骤继续。
  - 轮次为迭代轮：复盘最后一轮已写完则从 I1 开始；最后一轮只有主题、没有结果，则继续该主题。
- 后续需要的信息在这些文件里找不到时，只在题目描述或源码中搜索该点，读到后补写进 `notes/题目分析.md`。
- 显示"需复核"：重读题目描述并核对源码，更新题目分析后执行 `ctb.py analysis --done`。
- 题目还没拉取或分析未固化：从 B1 开始。

### 基线轮

- **B1 拉题与通读**
  - 读：`framework_rules.md` 全文；`methodology.md` 一、二节与三节"第 0 步"。
  - `ctb.py pull --subject <ID或URL>`（没有 Cookie 时会自动获取）。
  - 通读 `answer/题目描述.md`、`answer/题目补充信息.md`、`answer/udpunittest.py`、`answer/testaw.py`。
  - 用自己的理解写 `notes/题目分析.md`（结构见下方"题目分析"）。
- **B2 反编译定位接口**
  - `ctb.py decompile`，读 `decompiled/index.md`，从命令名定位每个命令的处理代码。
  - 每个接口只梳理：参数校验与返回码、返回文本格式、关键常量（上限、阈值）。业务细节留到迭代轮按主题深入。
  - 结论补进 `notes/题目分析.md`，来源标"源码"，作为待探针验证的假设。
- **B3 起草并审阅接口规格**
  - 读：`recording.md` 五节。
  - `ctb.py spec`，对照题目分析修正 `notes/spec.json`：删除误识别的命令，补全每个命令可能的返回码，修正 `code_pattern`；确认后把 `reviewed` 改为 `true`。
- **B4 快速探针**
  - 读：`methodology.md` 五节"时间与资源排布"。
  - 每个命令发一条合法命令和主要的非法分支，确认返回格式、失败返回码、系统生成标识的形态；确认标识与参数的合法边界、容量上限、时间规则。
  - 记下单条命令平均耗时；确认的数值写入 `notes/数值模型.md` 并注明探针记录文件名，题目分析同步改正；执行 `ctb.py analysis --done`。
- **B5 录制基线用例**
  - 写生成脚本前读：`methodology.md` 四、五、六节；`recording.md` 一、二、三节。第一次看录制结果前读：`recording.md` 四、六、八、九节；覆盖率报告"注意"提示分层存疑或核心类为空时，再读七节。
  - 在 `notes/steps/` 下写生成脚本，每个测试用 `#:` 行写一句场景描述；`ctb.py record --gen notes/steps/<名称>.py --dry-run --coverage` 迭代。
  - 基线质量门槛，全部满足即进入 B6：
    - 矩阵中没有"未调用"的命令，spec 中每个命令至少触发 1 个成功返回与 1 个失败返回码；
    - 用例满足 `methodology.md` 四节规模锚点（多对象、单用例操作数下限、合法与非法交错、逐条精确断言）；
    - 录制报告中两轮不一致的步骤已处理。
  - 不要求矩阵缺口清零、覆盖率不再提升，这些留给迭代轮。
- **B6 写入并本地全绿**
  - 读：需要手写用例时读 `assertion_patterns.md` 中对应写法的章节。
  - 去掉 `--dry-run` 执行 `ctb.py record --gen ...`，自动写入并执行 `check` + `local`；手写或调整后 `check` + `local` 直到全部通过，单用例耗时在上限内。
- **B7 平台调试**
  - 读：有报错或代码质量扣分时读 `framework_rules.md`"判题结果"。
  - `ctb.py run`（判题需要数分钟，按"后台任务进行中"的提示反复 `ctb.py wait`）。调试结果只说明代码能否在平台正常运行，不含 bug 命中。
  - 有报错或扣分项：修复后 `check` + `local`，再 `run`，直到平台运行正常。
- **B8 正式提交与复盘**
  - 读：`methodology.md` 八节；`recording.md` 十节。
  - `ctb.py submit --yes`（不需要征得用户同意），`wait` 到结束；阅读 bug 检出表与"命中记录"。
  - 按下方"复盘记录"写入 `notes/复盘.md`（第 1 轮），列出下一轮候选主题，然后进入迭代轮。

### 迭代轮（每轮一个主题，连续进行）

- **I1 选主题**
  - 读：第一次进入迭代轮时读 `methodology.md` 三节"迭代轮"；转入十节维度主题时读十节。
  - 从复盘最后一轮的候选主题中选一个，优先级：未命中 bug 的推测 → 覆盖率报告中未探索的缺口（没有"已探索"标记的未执行行、缺分支行、未执行方法）→ 矩阵缺口 → `methodology.md` 十节的场景维度。
  - 对照 `notes/场景库.md`，不选库中已有的场景（同样的命令组合、对象状态与数据形态）。
  - 开始前先在 `notes/复盘.md` 写下本轮标题与主题。
- **I2 深入探测**
  - 只读与主题相关的源码：覆盖率报告给出的源码位置、主题涉及的命令处理代码。
  - 针对主题做探针，确认分支条件、数值、状态变化；结论补进题目分析与数值模型。
- **I3 录制新场景**
  - 用新的测试名写新的生成脚本，`ctb.py record --gen ... --dry-run --coverage`。
  - 看覆盖率报告头的"相对已探索"与测试贡献表的"相对已探索新增行"、矩阵新触发的返回码：
    - 有新增：继续 I4；
    - 没有新增：调整步骤去走主题对应的分支；同一主题两次录制都没有新增，放弃该主题，记入复盘，回到 I1；
    - 主题是十节的场景维度（数值边界、累计跨阈值、状态组合与顺序等）时，覆盖行可能不增加，步骤确实体现了该维度即可继续 I4。
- **I4 写入并本地全绿**：同 B6。
- **I5 平台调试**：同 B7；`run` 输出"本版本相对已探索"的新增，没有新增且不是十节维度主题时回到 I1。
- **I6 正式提交与复盘**
  - `ctb.py submit --yes`；没有新增、主题是十节维度时用 `ctb.py submit --yes --reason "<维度说明>"`。
  - 输出提示本次检出少于历史最多的一次时：`ctb.py restore`，再 `run`、`submit --yes`。
  - 写完本轮复盘与候选主题后，检查停止条件；不满足就直接回到 I1 开始下一轮。
  - 核心覆盖率与矩阵已不再提升、命中数连续两轮不涨时，读 `methodology.md` 十节，候选主题改从十节的方法中产生。

### 停止条件

- 命中数连续三轮不涨，且十节的方法都已作为主题试过：`ctb.py status` 确认最后一次提交就是检出最多的版本（不是则 `restore` 后重新 `run`、`submit`），然后向用户汇报。
- 遇到无法自行解决的阻塞（登录失效且无法自动获取 Cookie、平台持续报错、后台任务超时）时停止并汇报。
- 除此之外不停下等待用户确认。

### 复盘记录（`notes/复盘.md`）

- 每轮一节，标题为轮次与主题；I1 开始时先写标题与主题，提交后补全其余各项。
- 各项：主题、新增用例（测试名与一句场景）、相对已探索新增（行、分支、返回码；用 `--reason` 提交时写理由）、检出变化（本轮检出、较上轮新增与丢失的 bug 编号）、保留的用例、放弃的主题与原因、下一轮候选主题（按优先级排列，至少 3 个）。

示例：

```
## 第 3 轮：容量上限与满额后的重复操作

- 主题：容量上限与满额后的重复操作
- 新增用例：test_cjl_07_capacity_full（12 个对象占满容量后重复申请与释放再申请）
- 相对已探索新增：行 14，分支 6，返回码 2（apply|E005、release|E007）
- 检出变化：5/12 → 7/12，新增 bug 4、9，丢失 无
- 保留的用例：test_cjl_01_base、test_cjl_04_transfer、test_cjl_07_capacity_full
- 放弃的主题：无
- 下一轮候选主题：
  1. 跨月结算时的累计清零
  2. 冻结状态下的全部写操作
  3. 金额 N-1/N/N+1 边界
```

## 题目分析（`notes/题目分析.md`）

- 用自己的话写理解结果，不复制题目原文；后续会话以它代替题目描述与源码。
- 章节：系统概述、接口、业务规则、数值与边界、时间规则、资源与容量、未确认。
- 接口：每个命令一条，写参数与合法范围、成功返回、每个失败返回码及其触发条件、对状态的影响。
- 每条结论标注来源：描述、源码、探针（探针注明记录文件名）；源码得出、尚未探针确认的标"待验证"。
- 不确定或描述与源码矛盾的点放进"未确认"，探针确认后移到对应章节。

## 硬性纪律

1. 不修改 `testtool.py`、`timeout.py`、`config.properties`（`udpPort` 由脚本管理）；`udpunittest.py` 的 `if __name__ == '__main__':` 段一个字符都不改；只使用 `MyTestCase1` 一个测试类。
2. 断言优先由 `record` 从无 bug 版本录制生成；手写断言中的每个数字都必须先经探针确认，并能在 `notes/数值模型.md` 里找到来源；禁止凭感觉或只凭源码写死数值。不手工修改 `ctb-record` 标记内的内容，需要调整就改步骤后重录。
3. 任何改动后都要重新 `check` + `local`，保持无 bug 版本全部通过；`run` 已强制执行这两步，不要绕过。
4. 探针通过 `ctb.py probe` 进行，不在 `answer/` 下创建文件；确需临时文件时用 `_probe*` 前缀并在用完后立即删除（`check` 会拦截残留）。
5. 只用 Python 标准库，代码兼容 Python 3.8；单个用例必须在 300 秒内完成（`local` 会给出每个用例耗时）。
6. 无 bug 版本运行时进程退出码可能非 0，以日志 `Ran N tests ... OK` 为准。
7. 自动识别结果（spec、覆盖率分层）都是草稿：spec 未审阅（`reviewed=false`）前，矩阵缺口仅供参考；分层有误时用 `notes/coverage/scope.json` 纠正，并在报告的"注意"中核对识别依据。
8. 录制只保证用例与无 bug 版本一致，能否检出 bug 取决于步骤设计；用矩阵、覆盖率与测试贡献检验步骤质量，不以"录制通过"或"覆盖率高"作为完成标准。
9. 长任务中上下文会被压缩：题目分析、数值模型、探针结论、复盘结论必须写进 `notes/`，复盘必须在开始下一轮之前写完；恢复时按第 0 步读 `notes/` 中的结论，参考资料只重读当前步骤列出的章节。
10. 被测程序的端口与进程由脚本管理：需要停止时用 `ctb.py stop`，不按进程名结束进程（如 `taskkill /IM java.exe`、`pkill java`），也不手工修改 `udpPort`。
11. 命名前缀（便于与队友代码合并，`check` 强制检查）：用例方法以 `test_cjl_` 开头（步骤文件中的测试名同样如此）；`testaw.py` 中的函数、类与 `MyTestCase1` 中新增的非用例方法以 `cjl_` 开头；全局常量以 `CJL_` 或 `cjl_` 开头。
12. 判题结果是确定的，同样的用例每次命中同样的 bug。命中保留的用例不再修改；新场景用新的测试名、写进新的生成脚本或新测试中，避免重录时改变已命中的用例（录制时会对此告警，并跳过与场景库中未命中场景步骤完全相同的测试）。
13. 长命令不重复执行：输出"后台任务进行中"后只执行 `ctb.py wait`，不要重新执行原命令（`run` / `submit` 重复执行会重复提交判题）；`wait` 出现"后台任务结束"才算命令完成，以其后的退出码与输出为准。命令行工具报超时或中断时，先 `ctb.py status` 查看后台任务，而不是重跑。同一步骤连续两次超时或报错相同、`wait` 显示的已用时间超过 30 分钟仍未结束时，停止并向用户汇报现象（需要时 `ctb.py cancel`），不要继续重试。
14. 调试与正式提交：`run`（调试）只验证代码能否在平台运行，看不到 bug 命中；bug 命中只来自 `submit --yes`（正式提交）。成绩以最后一次正式提交为准，所以最后一次提交必须是检出最多的版本。`submit` 要求当前答题文件已经 `run` 过，并拒绝提交删除或修改了上一轮命中保留用例的版本；不要用 `--force` 绕过，除非用户要求。
15. 不随意提交：迭代轮的提交必须相对已探索范围有新增覆盖行、分支或返回码；`--reason` 只用于确实采用了十节场景维度的主题，理由写具体维度，不写空泛理由。
16. 连续推进：各轮之间不停下等待用户确认，只在满足停止条件时汇报；每轮只做一个主题，不在一轮里堆多个主题。
