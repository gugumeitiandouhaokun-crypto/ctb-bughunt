# 录制、矩阵与覆盖率

录制把"写断言"变成"写步骤"：只描述要发送的命令序列，期望值由无 bug 版本的真实返回自动生成。接口规格与矩阵告诉你哪些接口行为还没被触发，分层覆盖率告诉你处理命令的代码中哪些分支、哪些行还没执行到。三者配合，用最少的人工把用例做大、做密、做准。所有自动识别都是草稿，以你的审阅为准。

## 一、步骤文件

### 约束

- UTF-8 文本，每行一条，首尾空白忽略；空行与 `#` 开头的行忽略。
- `== <测试名> ==` 开始一个测试方法。测试名以 `test_cjl_` 开头，只含 ASCII 字母、数字、下划线；同一文件内不可重复，也不可与 `udpunittest.py` 中其他方法重名。
- 第一个 `== ... ==` 之前不能出现命令；每个测试至少一条命令。
- 普通行是一条原样发送的命令。
- `#: <描述>` 是当前测试的场景描述，可写多行（拼接为一句），进入场景库；每个测试都要写，说明对象数、状态组合、数据形态与主要非法分支。
- `$变量 = 命令`：发送命令，把返回中第一个 `:` 之后的全部文本存入变量；返回中没有 `:` 时存空串。
- `$变量/正则/ = 命令`：发送命令，把正则第 1 个分组（无分组时取整体匹配）存入变量；不匹配时存空串。
- `${变量}` 在之后的命令中引用变量。变量只在当前测试方法内有效，且必须先捕获后引用（解析时校验）。
- 命令里不要带多余空格（`check` 会对含空格的命令字面量告警）。
- 每个测试开始前会发送 `init()`，测试之间不共享状态；测试按名称排序执行，与 unittest 的执行顺序一致。
- 单个测试的命令总耗时必须远小于 300 秒；录制报告给出每个测试的耗时，超过 250 秒要拆分。

### 示例

```
== test_cjl_01_multi_object ==
#: 2 个对象创建后交替消耗，一个超额，会话开关后查询统计
create_obj(A001,10)
create_obj(A002,20)
use_obj(A001,3)
use_obj(A002,25)
query_obj(A001)
query_obj(A002)
$sid = open_session(A001)
close_session(${sid})
$cnt/total=(\d+)/ = stat_obj(A001)

== test_cjl_02_illegal_input ==
#: 单对象下消耗量为 0、负数与不存在对象
create_obj(A001,10)
use_obj(A001,0)
use_obj(A001,-1)
use_obj(A999,1)
```

## 二、生成脚本

### 约束

- 规模大的场景用 Python 脚本生成步骤：脚本的标准输出就是步骤文件内容，格式同第一节。
- 脚本放在 `notes/steps/` 下，只用标准库；由 `ctb.py record --gen` 在工作目录下执行，输出另存为 `notes/steps/<名称>.steps.txt`。
- 录制名称默认取脚本/文件名（不含扩展名），只能含 ASCII 字母、数字、下划线；同名再次录制会整块替换上次的结果，不影响其他录制与手写用例。
- 一个脚本可以输出多个测试；按场景主题拆成多个脚本，便于单独重录。
- 用数据与循环描述场景：对象列表 × 操作轮次 × 参数取值（合法边界、非法值），合法与非法交错。

### 示例

```python
OBJECTS = ["A%03d" % i for i in range(1, 13)]


def emit(line):
    print(line)


emit("== test_cjl_01_multi_object ==")
emit("#: 12 个对象各自累积消耗 3 轮，每轮后逐个查询")
for i, obj in enumerate(OBJECTS):
    emit("create_obj(%s,%d)" % (obj, 10 + i))
for rnd in range(3):
    for i, obj in enumerate(OBJECTS):
        emit("use_obj(%s,%d)" % (obj, 1 + i + rnd * 5))
    for obj in OBJECTS:
        emit("query_obj(%s)" % obj)

emit("== test_cjl_02_illegal_input ==")
emit("#: 单对象下消耗量取 0、负数、下限、上限、超上限")
emit("create_obj(A001,10)")
for value in (0, -1, 1, 100, 101):
    emit("use_obj(A001,%d)" % value)
```

## 三、录制与断言生成

### 约束

- 录制在无 bug 版本上进行，同一进程内连续执行两轮：第 A 轮从全新启动开始，第 B 轮紧接着再执行一遍（每个测试前仍发 `init()`）。
- 每一步按两轮返回生成断言：
  - 两轮一致：精确断言整条返回。
  - 不一致，但把返回中出现的已捕获变量值替换为 `${变量}` 后两轮都能还原：模板断言，运行时用当次捕获的值填充后精确比较。
  - 仍不一致：只断言返回码（第一个 `:` 之前的部分），并列入录制报告的"两轮不一致"清单。
- 只断言返回码的步骤要逐条查看：常见原因是返回中含有时间、随机值、或未被 `init()` 复位的计数。能通过捕获变量（`$变量 = ...`）把可变部分纳入模板的，修改步骤后重录；确实不可预判的，保持现状或改为手写的格式/关系断言。
- 录制结果写入：
  - `answer/testaw.py`：运行时块（`cjl_run_steps` 等，只写一次）与数据表块 `cjl_steps_<测试名>`；
  - `answer/udpunittest.py`：每个测试一个 `@timeout(global_default_timeout)` 方法，调用 `testaw.cjl_run_steps(self, testaw.cjl_steps_<测试名>)`，插在 `# 提示：联调函数` 注释之前。
- 写入区域以 `# ==== ctb-record ... begin/end ====` 标记包围，不要手工修改标记内的内容（重录会覆盖）；需要手工调整的断言写成标记外的独立用例。
- `udpunittest.py` 必须已有 `import testaw`、`from timeout import timeout` 与 `global_default_timeout`，否则不做任何修改并报错。
- 录制写入后自动执行 `check` 与 `local`；失败时按 `local` 输出的"step N: 命令 expect 期望 actual 实际"定位。
- 断言失败消息格式：`step <序号>: <实际发送的命令> expect <期望> actual <实际>`，序号从 1 开始，对应步骤文件中该测试的第几条命令。
- 数据表的代码质量以判题返回的扣分项为准；如被扣分，按扣分项调整表的组织方式并记入 `notes/复盘.md`。

### 数据表示例

```python
cjl_steps_test_cjl_01_multi_object = (
    ('create_obj(A001,10)', 'E000:Success'),
    ('use_obj(A001,3)', 'E000:7'),
    ('open_session(A001)', 'E000:${sid}', 't', 'sid'),
    ('close_session(${sid})', 'E000:Success'),
    ('stat_obj(A001)', 'E000:total=7', 'e', 'cnt', 'total=(\\d+)'),
    ('tick()', 'E000:1712', 'p'),
)
```

## 四、录制报告（`notes/record/<名称>.md`）

### 约束

- 汇总：测试数、步骤数、精确/模板/仅返回码断言的条数；`init()` 未返回成功的测试。
- 测试表：每个测试的步骤数与录制耗时，超过 250 秒标注需拆分。
- 命令分布：每个命令的调用次数、返回码分布、不同返回的数量。用它检查步骤是否有效：
  - 某命令几乎全是失败返回码：前置状态没搭好，合法路径没走到；
  - 某命令没有任何失败返回码：非法分支没覆盖；
  - 某命令"不同返回"只有 1 个：数据形态单一，补不同参数、不同状态下的调用。
- 两轮不一致清单：测试名、第几步、步骤文件行号、两轮返回。
- 同目录下的 `<名称>.json` 保存每步的命令与两轮返回，供矩阵汇总；dry-run 也会保存。

## 五、接口规格（`notes/spec.json`）

### 约束

- `ctb.py spec` 起草，草稿规则：
  - 命令：题目描述中出现的"名称(参数)"；反编译业务代码中既是字符串常量又是方法名的标识符也会列入（来源只有 jar，需确认）。
  - `code_pattern`：描述中"<码>:<文本>"示例里 <码> 的最常见形状（正则），用于从返回中取返回码；未识别时按第一个 `:` 之前的部分取。
  - 各命令返回码：描述中从该命令首次出现到下一个命令首次出现之间、匹配 `code_pattern` 的码；第一个命令之前出现的码进 `common_codes`（所有命令都可能返回）。
  - `jar_codes`：反编译源码中匹配 `code_pattern` 的码，供补全时参考。
- 审阅要求：
  - 删除不是被测命令的条目（描述中的举例函数、说明性文字中的括号等）。
  - 每个命令的 `codes` 只列对外可见的返回码：题目描述列出的，或探针、录制的实际返回中出现过的。源码中存在、但对外被统一包装成别的返回的内部码不列入。
  - 源码中有、描述与实际返回中都没出现过的码，对照源码的返回路径确认能否原样返回给调用方：能返回的列入；确认被包装的不列入。
  - 所有失败都返回同一个码（或同一段文本）时，在 `notes/题目分析.md` 记录"失败统一返回 <返回>，失败原因靠覆盖率区分"，不为内部原因单独列码。
  - 命令名以实际发送的大小写为准。
  - 审阅完成后把 `reviewed` 改为 `true`。
- 再次执行 `ctb.py spec` 只追加相对上次自动提取新增的命令与码，并把 `reviewed` 置回 `false`；`--force` 丢弃人工修改重新生成。
- spec 用于矩阵对照和覆盖率分层（入口方法匹配）；缺少 spec 时，覆盖率改用录制与探针中出现过的命令名。

### 示例

```json
{
  "reviewed": true,
  "code_pattern": "[A-Z]\\d{3}",
  "common_codes": ["E999"],
  "jar_codes": ["E000", "E001", "E002", "E999"],
  "commands": {
    "create_obj": {"signature": "create_obj(id,size)", "codes": ["E000", "E001", "E002"], "source": ["desc", "jar"]},
    "query_obj": {"signature": "query_obj(id)", "codes": ["E000", "E001"], "source": ["desc", "jar"]}
  }
}
```

## 六、接口 × 返回码矩阵（`notes/matrix.md`）

### 约束

- 数据来源：`notes/record/*.json`（第 A 轮，含每个测试前的 `init()`）与 `notes/probes/*.txt`。`record` 结束时自动刷新并打印缺口，也可单独执行 `ctb.py matrix`。
- 缺口类别与处理：
  - 未调用：spec 中的命令一次都没发送过，补调用。
  - 未触发：命令的某个返回码在该命令上没出现过，而系统在别的命令上返回过它（确定对外可见），对照源码找出返回该码的条件，构造步骤触发。
  - 从未出现：返回码在所有命令的任何返回中都没出现过。对照源码的返回路径：对外确实会返回的，构造步骤触发；被包装、对外不会出现的，从 spec 中删除。
  - 单一返回码：命令只出现过一种返回码，说明合法或非法分支缺一侧。
  - 规格外：实际出现了 spec 没有的命令或返回码，先确认是否 spec 漏写，再决定补 spec 还是修正步骤。
- 确认在无 bug 版本中无法触发的返回码（如复位命令的失败码），在 `notes/复盘.md` 记录原因，不必强行触发。
- "返回文本形态"列出每个命令每个返回码下不同返回文本的种数与示例；文本在所有调用中完全相同的返回码另行提示：同一返回码下的不同失败原因从返回上区分不开，不算缺口，用覆盖率（第八节的缺分支行）判断各失败分支是否走到，并在失败步骤后加查询步骤核对状态没有被改动。

## 七、覆盖率分层

### 约束

- `ctb.py record ... --coverage` 统计本次录制（并给出每个测试的贡献）；`ctb.py coverage` 带覆盖率跑一次完整的 `local`（含手写用例与所有录制），反映提交物整体的覆盖。
- 只统计业务类（排除常见三方库），再分三层：
  - 核心：含入口方法的类。入口方法指方法名与命令名去下划线、忽略大小写后相同；且该类匹配到至少 2 个命令，或所匹配的命令只在这一个类中有同名方法（只有 1 个命令时不限）。只匹配到一个多处同名命令方法的类不计入核心，并在报告"注意"中列出。
  - 相关：含命令名字符串常量的类（命令分发）；核心类引用的业务类；再由这些类引用、且与某个核心类同包的类；核心/相关类的内部类。
  - 基础设施：其余业务类（通信、日志、启动、工具等），只汇总一行，不计入主指标。
- 一个入口方法都匹配不到时（如方法名被混淆），录制模式下改用"启动基线中未执行、命令执行后才执行"的类作为核心；仍无法判断时报告会提示，需要填写 `notes/coverage/scope.json`。
- `notes/coverage/scope.json` 按类名前缀（`.` 或 `/` 分隔均可）指定分层，优先于自动判断，按 exclude、related、core 的顺序应用（后者覆盖前者）。
- 主指标是核心类的行、分支、方法覆盖率，摘要追加到 `notes/coverage/history.md`，并给出与同一来源（同名录制或 `local`）上次结果的差值。
- 相关类中常含有在无 bug 版本中走不到的代码（构造器重载、`equals`/`hashCode`、调试与故障注入代码），其低覆盖不必追求。
- 工作目录路径含空格或非 ASCII 字符且无法转换为短路径时，覆盖率不可用，需换到纯英文路径。

### scope.json 示例

```json
{
  "core": ["com.example.service.impl.OrderServiceImpl"],
  "related": ["com.example.model."],
  "exclude": ["com.example.log.", "com.example.net."]
}
```

## 八、未执行行定位

### 约束

- 报告的"部分覆盖的方法"按核心在前、缺口多的在前列出，每个方法后给出其在反编译源码中的声明位置（相对 `decompiled/src/`）。
- 方法下逐条列出：
  - `L<n> 未执行`：原始源码第 n 行一次都没执行；
  - `L<n> 缺 m/k 分支`：该行共 k 个分支，有 m 个没走到。
- 原始行号与反编译源码行号不同。报告用 class 文件中该行引用的常量、方法、字段在方法体内匹配反编译源码行，给出 `→ :<反编译行号> <源码>`；匹配不到时给出"线索"（该行引用的常量与名称），按线索在方法体内搜索。
- 处理顺序：先看"缺分支"的条件行，确定未走到的是条件为真还是为假的一侧，再看紧随其后的"未执行"行（通常是该分支的处理或返回）。构造满足条件的输入或状态加入步骤。
- 已有正式提交时，被历次提交的用例执行过的行、分支已全部走到过的行、执行过的方法标"（已探索：历次提交的用例执行过）"并排在同类条目之后：这些位置已经测过且命中结果已知（用例因未命中被精简删除），不作为新主题。

## 九、测试贡献（录制时）

### 约束

- 录制时在启动后、每个测试结束后分别采集覆盖数据，扣除启动基线（启动与首次复位执行的代码）后统计核心+相关类：
  - 覆盖行：该测试执行到的行数；
  - 独有行：只有该测试执行到的行数；
  - 按顺序新增分支：按测试名顺序累计，该测试新走到的分支数；
  - 相对已探索新增行：该测试执行到、历次正式提交的用例都没执行过的行数（还没有正式提交时为 `-`）。
- "冗余候选"只表示该测试没有独有覆盖。多对象累积、长状态链、大量数值组合的测试即使没有独有行也有检出价值（bug 常在已执行代码的数值与顺序细节上），不要仅凭覆盖删除；真正重复的场景再合并或删除。
- 测试贡献只统计本次录制文件中的测试；整体覆盖看 `ctb.py coverage`。

## 十、命中记录、用例精简与场景库

### 约束

- 只有正式提交（`ctb.py submit --yes`）的判题结果含 bug 命中；提交判题后自动执行，依据每个 bug 的触发用例名与 `notes/local_last.json` 中的本地耗时：
  - 每个已检出的 bug 保留命中它、耗时最短的一个用例（耗时相同时取命中 bug 更多的）；
  - 其余用例删除：未命中任何 bug 的，以及命中的 bug 都已由保留用例覆盖的；
  - 有已检出的 bug 对应不到任何用例时，本轮不删除任何用例；
  - 题目原件 `udpunittest.py` 自带的样例用例（不以 `test_cjl_` 开头）不删除、不参与命名检查，也不要改名或删除；
  - `--no-prune` 只记录不删除，之后可用 `ctb.py prune` 补做（判题后答题文件有改动则拒绝）。
- 精简删除是预期行为，不是误判：保留的用例照样命中全部已检出的 bug，被删用例的场景记入场景库，探索过的范围记入已探索范围。删除的用例再多也不要 `restore` 或重新提交。
- 成绩以最后一次正式提交为准：
  - 每次提交时的答题文件与检出结果存到 `notes/submits/<时间>/`；
  - 只有提交输出提示"本次检出少于历史最多"时才用 `ctb.py restore`，它恢复检出最多那次的答题文件；最近一次提交已是检出最多时 `restore` 拒绝执行（`--name` 指定记录名时不限）；
  - 上一轮命中保留的用例被删除或内容被修改时，`submit` 拒绝提交并列出这些用例；
  - 当前答题文件没有 `run` 过（或 `run` 之后有改动）时，`submit` 拒绝提交。
- 判题结果是确定的：同样的用例每次命中同样的 bug，所以一轮未命中的用例直接删除。
- 删除录制用例会同时删除 `testaw.py` 中对应的 `cjl_steps_` 表与变空的录制标记块；手写用例删除整个方法（含装饰器），其辅助函数保留。
- `notes/场景库.md` 每轮追加一节，每个用例一条：命中状态与 bug 编号、来源（录制名或手写）、场景描述（录制取 `#:` 行，手写取方法 docstring）、步骤数与耗时、命令与返回码分布。
- `notes/hits.json` 记录每轮各用例命中的 bug 与场景步骤指纹（录制用例按命令模板序列，手写用例按方法源码）：
  - 录制时与"未命中""命中已替代"场景步骤完全相同的测试不写入答题文件；
  - 与已有用例步骤相同但换了测试名的测试不写入；
  - 命中保留的用例步骤发生变化时告警。
- 以前命中过、本轮没有任何用例命中的 bug 会在输出中提示：说明命中它的用例被修改或删除了，需恢复该用例或在复盘中说明。
- 手写用例在方法 docstring 中写场景描述，要求同 `#:` 行。

### 已探索范围与提交门槛

- `notes/explored.json` 是已探索范围：历次正式提交的用例执行过的核心+相关类代码行（含已覆盖分支数）与触发过的 `命令|返回码`。每次提交判题结束后并入，被精简删除的用例探索过的范围仍保留。
- `ctb.py run` 的本地验证带覆盖率运行，统计当前答题文件版本的覆盖行与返回码（返回码取自录制原始结果，手写用例不计），打印"本版本相对已探索"的新增行、新增分支、新增返回码。
- `ctb.py submit` 的门槛：
  - 还没有正式提交（基线轮）或答题文件是 `restore` 恢复的版本时不检查；
  - 新增行、新增分支、新增返回码都为 0 时拒绝提交；
  - `--reason "<维度说明>"` 在没有新增时允许提交，用于第十节的场景维度（数值边界、累计跨阈值、状态组合与顺序等），理由记入 `notes/submits/<时间>/meta.json`；
  - `run` 时覆盖率统计失败（没有当前版本的覆盖记录）按没有新增处理。
- `ctb.py status` 显示当前轮次、已探索范围大小与最近一次提交的新增和理由。
